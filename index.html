Grok Bot 使用指南

深度讲解 · 先原理与能力层 · 再实操验证

前言

这份指南不再是简短条目，而是把每一项都展开说明：它是什么、为什么这样设计、实际使用时要注意什么、常见误区和社区真实做法。

阅读建议：先完整看完「核心原理」和「连接器、插件与 Skills」，再看例程与进阶，最后用实操案例验证。核心主线仍然是：先搜索现有 Bot → 异步发送并等待最终结果 → 把验证过的流程做成 Skill → 再挂到例程上。

核心原理

什么是 Grok Bot

Grok Bot 不是单次对话的聊天窗口，而是一个长期存在的代理。每个 Bot 拥有自己的名称、职责描述、独立对话历史和长期记忆。所有 Bot 共享一台属于你的云电脑，这台电脑有浏览器、文件系统和终端，并且可以保持登录状态。

这意味着：你可以关闭笔记本，Bot 仍能继续执行已安排的工作；浏览器里已登录的会话可以被后续任务复用；文件可以跨对话保留。官方文档把它描述为「有自己电脑的队友」，社区用户也经常用「员工」或「助理团队」来理解它。

和普通对话的关键区别在于：记忆和状态会跨轮次保留，并且可以主动安排在你不在时运行的任务。

何时使用 Bot，何时直接对话

适合交给 Bot 的典型场景：

  • 需要每天或定期重复的检查、摘要、监控
  • 需要在你离开后继续运行的工作
  • 需要记住长期偏好、项目状态或历史决策
  • 涉及你电脑上的文件、已安装程序或已登录浏览器
  • 跨多个服务的流程（例如邮件 → 表格 → 日历提醒）

不适合用 Bot 的情况：一次性问答、临时生成内容、不需要记忆和后台运行的简单查询。判断标准很简单：如果这件事需要「记住上次的情况」或「在我离开后继续做」，就考虑 Bot；否则直接对话更高效。

社区常见建议是「一个 Bot 一个清晰的岗位」，而不是做一个什么都能聊的大而全 Bot。岗位越清晰，记忆和例程越容易管理。

记忆机制详解

每个 Bot 有独立的长期记忆。它会记住你明确要求它记住的事实、对话中的关键决定、偏好以及已完成任务的状态。记忆不是无限的，重要信息最好明确告知，而不是假设它会自动提取。

不要把密码、API 密钥等敏感凭证放进记忆，这些应通过官方连接器或安全方式处理。当事实发生变化时，要主动告诉 Bot 更新，而不是假设它会自动感知。

社区还有一个实用技巧：把长期有效的规则写进 Bot 的描述（profile）里，而不是只放在聊天记录中。因为聊天历史会变长，而描述是相对稳定的锚点。另外，复制 Bot 时会保留描述、Skills 和例程，但不会复制对话历史和学到的记忆，这点在重置上下文时很有用。

连接器、插件与 Skills

三者分别是什么，如何配合

连接器 / 插件 是 Bot 访问外部服务的结构化方式。在侧边栏的「Connect apps」里添加，完成一次 OAuth 登录后，账号内的所有 Bot 都可以使用。常见的有 Gmail、Google Calendar、GitHub、Notion、Slack 等。优先使用连接器，因为它比纯浏览器点击更稳定、更不容易因为页面变化而失效。

Skills 是可复用的「怎么做」。一个好的 Skill 会明确写出：什么情况下使用、需要哪些输入和权限、具体步骤、如何验证结果、返回什么、哪些动作必须停下来等人确认。Skills 存在你的私有库里，可以在多个 Bot 之间共享（前提是 Bot 有相应的连接器或登录状态）。在对话里用 / 可以引用已保存的 Skill。

例程（Routine） 决定「什么时候做」。它把一个已验证的 Skill 或流程绑定到某个时间点或事件上，由特定的 Bot 负责执行。

正确的建立顺序是：先用连接器拿到可靠数据 → 在对话里把流程做对并保存为 Skill → 确认 Skill 稳定后再创建例程。直接把未验证的流程设成定时任务，很容易反复出错。

Teach a Task 的用法与限制

在支持的环境里，你可以让 Bot 观察你完成一次浏览器流程（最长约 10 分钟），它会自动生成一个 Skill 草稿。这个功能适合重复性强、规则清晰、错误成本低的操作。

但生成的只是草稿。你需要手动补充决策规则（为什么选这条路）、失败时怎么处理、哪些步骤必须审批。不要在演示过程中暴露密码；凭证应通过安全方式交接。之后一定要在安全的测试输入上完整跑一遍，确认无误后再考虑挂到例程上。

如果 Teach a Task 不可用，就用文字把步骤写清楚，然后明确要求保存为 Skill。

实用建议与常见误区

  • 能用连接器就不要只靠浏览器点击，稳定性差很多。
  • Skill 必须写清楚「何时使用、需要什么、如何验证、什么必须审批」，否则后面很难复用。
  • 在对话里用 / 调用 Skill，用 @ 提到 Bot、例程或连接器。
  • 没有插件的服务仍可通过共享电脑的浏览器操作，但需要你先登录一次，会话会保留。
  • 误区：以为装了插件就等于 Bot 会自动正确使用。实际上还需要在 Skill 或提示里明确说明数据来源和操作边界。

例程机制详解

一个完整的例程包含：负责的 Bot、触发条件（时间或支持的事件）、要执行的流程、输入来源、期望输出、审批边界、无数据或失败时的处理方式。

时间触发的例子：「每个工作日早上 8 点」。事件触发的例子：「当 GitHub 有新的 Pull Request 时」（需要相应集成支持）。事件触发的匹配规则要尽量窄，否则容易产生大量噪音。

好的例程提示必须自包含，因为执行时你不在旁边解释。要写明：从哪里拿数据、怎么处理、输出什么格式、如果数据缺失或过期怎么办、哪些动作（发送、修改、支付等）必须停下来等人确认。

官方和社区提到的限制：单个 Bot 最多约 50 个例程；计划间隔至少 5 分钟；系统保留最近约 20 条运行记录；删除后不可恢复。重要的是，隐藏 Bot 并不会停止它的例程，必须主动暂停或删除。

建议先用「Test run」在安全输入上验证，再正式启用。高频例程会快速消耗用量，社区普遍建议从每天几次或每小时一次开始，而不是更密。

正确交互流程

  1. 先搜索：分配任务前先搜索现有 Bot，看是否已有合适的岗位，避免重复创建。
  2. 异步发送并持续等待：必须使用异步模式发送，获得句柄后持续等待最终结果。只看确认回复就停止，容易错过真正的输出。
  3. 把成功流程保存为 Skill：流程在对话里验证通过后，明确要求保存为 Skill，并补充边界和校验规则。
  4. 需要自动化时再创建例程：写清触发条件、输入来源、失败处理和审批边界。
  5. 多 Bot 可能承担同一职责时先询问：不要自行决定，先列出候选让你选择。

这个流程可以减少重复创建、降低出错概率，也让长期维护更清晰。

进阶机制

四要素框架

社区常用的搭建方式可以归纳为四个要素：

  • Context：你是谁、业务目标、语气、硬性约束。这些最好写进 Bot 描述或共享文档里。
  • Connections：能可靠读写的工具（连接器优先）。
  • Capabilities：已验证的 Skills / SOP。
  • Cadence：例程的触发频率与退出条件。

缺少任何一个，系统都容易变成「能聊但做不好」或「经常出错还浪费用量」。

审批边界与成本控制

发送邮件、支付、删除文件、发布内容、修改生产系统等动作，必须在 Skill 和例程里明确要求停下来等人确认。社区用户普遍把「写操作必须审批」作为默认规则。

高频例程会快速消耗用量。建议从较低频率开始，并定期审计：哪些例程还在产生价值、哪些可以关掉、哪些记忆需要更新。每周花 15 分钟和 Chief of Staff 回顾一次，是多个用户验证过的有效做法。

多 Bot 协作的常见模式

一种是 Chief of Staff 作为唯一入口：你日常只和它对话，它负责判断该转给哪个专家 Bot。另一种是 Outer Loop / Inner Loop：一个 Bot 只负责调研和整理上下文，产出自包含的任务说明；另一个 Bot 只负责执行，不自己再去探索。这两种方式都能减少上下文污染和职责重叠。

社区案例研究

案例 A：一人公司 8 Agent + 11 Routine

一位 solopreneur 的做法是先创建 Chief of Staff，再按角色逐步添加专家 Bot（CMO、CFO、设计师、分析师等）。每个重复任务单独绑定到对应 Bot 的例程上，而不是全部堆在一个对话里。工具也是逐步连接的，而不是一次接完所有服务。

可借鉴点：先有一个总控，再按职责拆分；从高频、可验证的小事开始，成功后再扩大范围。

案例 B：产品经理 Swarm（7 个 Bot）

包含研究、策略、营销、设计、规格、工程和一个产品负责人。他们共享一个协作 Skill，让 Bot 之间知道如何交接。研究 Bot 的每周例程会扫描竞品定价、Changelog 和社交动态，如果没有变化就直接结束，不产生无用输出。

可借鉴点：共享协作规则；例程要有明确的「无变化则停止」退出条件，避免噪音。

案例 C：Chief of Staff 作为唯一入口

多位用户（包括管理 20+ 和 29 个 Bot 的配置）都采用类似模式：日常只和 Chief of Staff 对话。它的描述里写明「先检查是否有专家 Bot 负责，再决定自己做还是转交」。每周固定短时间回顾：它学到了什么、哪些地方被纠正过两次、哪些例程该关掉。

可借鉴点：把「先委托再执行」写进描述；定期审计例程和记忆，防止系统逐渐膨胀。

案例 D：Outer Loop / Inner Loop

Outer Loop Bot 只做调研和整理上下文，产出一份自包含的任务说明；Inner Loop Bot 只执行，不自己再去探索。适用于编码、复杂调研等需要清晰分工的场景。

可借鉴点：把「理解问题」和「执行动作」拆开，减少上下文污染，也让每个 Bot 的职责更清晰。

案例 E：真实生活与工作系统

社区用户公开的配置包括：礼物清单与预算提醒、行程比较、车辆保养记录、发票草稿、学习资料生成、周末活动推荐、家居维护日志、从邮件提取待办到提醒事项等。每个领域一个 Bot，写操作都留审批，从小事开始验证后再扩大。

可借鉴点：从高频、低风险、可验证的小事开始，成功后再逐步扩大范围，而不是一开始就追求大而全。

实操案例

以下案例可直接复制发给 Grok 测试。建议按顺序做，每个大约 1–2 分钟。做的时候注意观察系统是否先搜索、是否使用异步并等待最终结果。

案例 1：创建并测试记忆

目标：验证 Bot 能记住你明确告知的信息，并在后续对话中正确调用。

第一步： 
请创建一个新的 Bot，名称叫「测试助手」，描述是「用于练习记忆功能的 Bot」。
第二步： 
请让「测试助手」记住：我的测试关键词是「香港公司」，以后只要提到这个词就提醒我它记住了。

之后再问：「你记得我的测试关键词是什么吗？」观察是否正确回答，以及是否主动提醒。

案例 2：设置简单例程

目标：体验「在你离开时自动执行」，并确认例程已保存。

试试这个： 
请让「测试助手」保存一个例程：每天早上 8 点，检查是否有新消息，如果没有就回复「今日无新消息」。把这个例程保存下来。

设置后问：「现在有哪些例程？」确认已保存，并查看触发条件是否正确。

案例 3：搜索现有 Bot 并分配

目标：养成先搜索再创建的习惯，避免重复。

试试这个： 
请搜索现有的 Bot，看看有没有适合做「每日摘要」的。如果有，告诉我候选；如果没有，再建议是否需要新建。

观察系统是否先搜索，而不是直接创建新的。

案例 4：电脑操作任务

目标：理解 Bot 使用的是你的电脑环境，而不是独立的工作区。

安全测试： 
请让拥有电脑的 Bot 列出我下载文件夹里最近 5 个文件的名称（如果有的话）。不要修改任何文件。

如果返回了真实文件名，说明它确实在你的电脑上操作。

案例 5：修改与停止例程

目标：练习修改和清理例程，避免无效任务持续运行。

试试这个： 
请让「测试助手」把之前的每日例程改成「每天晚上 9 点执行」，并确认已更新。

然后再说「请删除这个例程」，观察是否成功。之后可以再问一次当前例程列表确认。

案例 6：服务集成

前提：相关服务（如 Gmail）已连接。目标：体验连接器带来的结构化访问。

试试这个： 
请搜索是否已有邮件相关 Bot。如果有，让它生成今天未读邮件的简短摘要（最多 5 封）。如果没有连接，请告诉我需要授权什么。

信息来源与社区经验

本指南的信息来自三个层面：

  • 平台内部机制：实际调用工具时的规则（搜索优先、必须异步、持续等待、例程由提示+触发条件组成、共享云电脑等）。
  • 官方文档：docs.x.ai/grok-bot 相关页面（overview、bots、skills-routines、computer-and-apps 等）。
  • 社区实践：Sawyer Merritt 的实操教程、@bot 团队分享的 power-user tips、solopreneur / Product Compass / Chief of Staff 模式的公开分享，以及真实用户的多 Bot 配置案例。

高频可借鉴技巧：一个 Bot 一个清晰岗位、用 Chief of Staff 协调、例程不要过频、Teach a Task 后完善 Skill、重要写操作留审批、定期审计例程和记忆。

总结

先建立清晰的能力层（连接器提供可靠访问，Skills 固化「怎么做」），再通过例程实现自动化。用实操案例验证流程是否正确。遇到具体问题时，把 Grok 的完整回复发回来，可以继续定位和调整。
