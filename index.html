Grok Bot 深度使用指南

每项详细讲解 · 案例含步骤原因与目的 · 复杂测试场景

前言

本版指南把每个主要分类写成可独立阅读的详细教程，而不是简短条目。阅读时请注意区分三层：原理（为什么这样设计）、操作（具体怎么做）、验证（如何确认做对了）。

社区经验表明，多数失败不是因为功能不存在，而是因为顺序错了、边界没写清、或者把未验证的流程直接自动化。因此本指南特别强调「先验证再固化，再自动化」的顺序。

核心原理（详细教程）

1. Bot 与普通对话的本质区别

普通对话是无状态或弱状态的。每次新开窗口，上下文基本从零开始。Grok Bot 则是长期存在的代理：它有名称、职责描述、独立对话历史、长期记忆，并且运行在一台共享的云电脑上。

这台云电脑有浏览器、文件系统和终端。浏览器的登录会话可以跨任务保留。文件可以跨对话存在。工作可以在你关闭设备后继续。官方把它描述为「有自己电脑的队友」，社区用户常用「员工」或「助理团队」来理解。

为什么这很重要：很多任务不是「问一次就结束」，而是需要记住上次的状态、继续处理文件、或在特定时间主动检查。普通对话做不到这些，Bot 可以。

常见误区：以为 Bot 只是「能记住东西的聊天」。实际上它还拥有执行环境。如果你需要操作本地文件、已登录网站或后台持续运行的任务，必须交给 Bot，而不是普通对话。

2. 何时创建 Bot，何时直接对话

判断标准可以具体化为三个问题：

  • 这件事是否需要记住上次的决定或状态？
  • 这件事是否需要在我离开后继续执行？
  • 这件事是否涉及我的文件、已登录浏览器或已连接的服务？

如果三个问题都是「否」，直接对话更高效。如果有任何一个是「是」，就考虑 Bot。

社区高频建议是「一个 Bot 一个清晰的岗位」。岗位越清晰，记忆越不容易污染，例程越容易管理，出问题时也更容易定位。不要做一个「什么都能聊」的通用 Bot，然后把所有事情都丢给它。

实际操作时，先搜索现有 Bot。如果已有职责接近的，优先复用或调整描述，而不是新建。重复创建会导致维护成本上升，也容易出现职责重叠。

3. 记忆机制的实际运作

每个 Bot 有独立的长期记忆。它会保留你明确要求记住的事实、对话中的关键决定、偏好，以及已完成任务的状态。记忆不是无限的，重要信息最好明确告知。

敏感信息（密码、API 密钥、私人凭证）不要放进记忆。这些应通过官方连接器或安全方式处理。当事实发生变化时，要主动更新，而不是假设 Bot 会自动感知。

社区实用技巧：把长期有效的规则写进 Bot 的描述（profile）里，而不是只放在聊天记录中。聊天历史会变长，描述是相对稳定的锚点。复制 Bot 时会保留描述、Skills 和例程，但不会复制对话历史和学到的记忆，这在需要重置上下文时很有用。

定期审计记忆也很重要。可以问 Bot「你目前记住了哪些关键事实」，然后纠正过时或错误的内容。否则错误会在后续任务中被反复引用。

连接器、插件与 Skills（详细教程）

1. 连接器 / 插件是什么

连接器（在界面里常叫插件）是 Bot 访问外部服务的结构化方式。在侧边栏的「Connect apps」里添加，完成一次 OAuth 登录后，账号内的所有 Bot 都可以使用。常见的有 Gmail、Google Calendar、GitHub、Notion、Slack 等。

为什么优先用连接器而不是浏览器点击：连接器提供稳定的结构化接口，不容易因为网页改版而失效。浏览器点击适合没有连接器的服务，或者需要视觉判断的操作，但稳定性较差。

添加后，在对话里用 @ 可以明确引用某个连接器。安装是账号级的，不是单个 Bot 独占。

2. Skills 的设计原则

Skill 是可复用的「怎么做」。一个完整的 Skill 应包含：

  • 什么情况下使用它
  • 需要哪些输入和权限
  • 具体步骤
  • 如何验证结果是否正确
  • 返回什么格式
  • 哪些动作必须停下来等人确认

Skills 存在私有库里，可以在多个 Bot 之间共享（前提是 Bot 有相应的连接器或登录状态）。在对话里用 / 可以引用已保存的 Skill。

正确建立顺序：先在对话里把流程做对 → 明确要求保存为 Skill，并补充边界和校验规则 → 在安全输入上测试 → 确认稳定后再考虑挂到例程上。

3. Teach a Task 的用法与限制

在支持的环境里，可以让 Bot 观察你完成一次浏览器流程（最长约 10 分钟），它会生成一个 Skill 草稿。适合重复性强、规则清晰、错误成本低的操作。

生成的只是草稿。你需要手动补充决策规则、失败处理方式和审批边界。不要在演示中暴露密码。之后一定要在安全的测试输入上完整跑一遍，确认无误后再使用。

如果 Teach a Task 不可用，就用文字把步骤写清楚，然后明确要求保存为 Skill。

例程机制（详细教程）

例程的完整组成

一个可用的例程至少包含：负责的 Bot、触发条件（时间或支持的事件）、要执行的流程、输入来源、期望输出、审批边界、无数据或失败时的处理方式。

时间触发例子：「每个工作日早上 8 点」。事件触发例子：「当 GitHub 有新的 Pull Request 时」（需要相应集成支持）。事件触发的匹配规则要尽量窄，否则容易产生大量噪音。

好的例程提示必须自包含，因为执行时你不在旁边解释。要写明从哪里拿数据、怎么处理、输出什么格式、如果数据缺失或过期怎么办、哪些动作必须停下来等人确认。

限制与最佳实践

单个 Bot 最多约 50 个例程；计划间隔至少 5 分钟；系统保留最近约 20 条运行记录；删除后不可恢复。隐藏 Bot 并不会停止它的例程，必须主动暂停或删除。

建议先用「Test run」在安全输入上验证，再正式启用。高频例程会快速消耗用量，社区普遍建议从每天几次或每小时一次开始，而不是更密。定期审计：哪些例程还在产生价值，哪些可以关掉。

正确交互流程（详细）

  1. 先搜索：分配任务前先搜索现有 Bot。目的是避免重复创建，减少职责重叠。
  2. 异步发送并持续等待：必须使用异步模式，获得句柄后持续等待最终结果。目的是确保拿到真正的输出，而不是只看到确认。
  3. 把成功流程保存为 Skill：流程验证通过后明确要求保存，并补充边界。目的是让后续可以复用，而不是每次重新描述。
  4. 需要自动化时再创建例程：写清触发、输入、失败处理和审批。目的是让任务在你不在时可靠运行。
  5. 多 Bot 可能承担同一职责时先询问：列出候选让你选择。目的是避免系统自行决定导致混乱。

进阶机制（详细）

四要素框架

Context（你是谁与约束）、Connections（可靠的工具访问）、Capabilities（已验证的 Skills）、Cadence（例程节奏）。缺少任何一个都容易出现「能聊但做不好」或「经常出错还浪费用量」。

审批边界与成本控制

发送、支付、删除、发布、改生产系统等动作必须在 Skill 和例程里明确要求停下来确认。高频例程会快速消耗用量。每周短回顾（哪些学到了、哪些被纠正过两次、哪些例程该关）是多个用户验证过的有效做法。

多 Bot 协作模式

Chief of Staff 作为唯一入口：日常只和它对话，它负责判断该转给哪个专家。Outer Loop / Inner Loop：一个只做调研并产出自包含任务说明，另一个只执行。两种方式都能减少上下文污染。

社区案例研究（含步骤原因与目的）

案例 A：一人公司 8 Agent + 11 Routine

步骤 1：先创建 Chief of Staff。目的：建立一个统一入口，避免你直接管理多个 Bot。

步骤 2：按角色逐步添加专家 Bot（CMO、CFO 等）。目的：每个 Bot 职责单一，记忆和例程更容易维护。

步骤 3：每个重复任务单独绑定到对应 Bot 的例程。目的：失败时容易定位，也方便单独暂停。

步骤 4：工具逐步连接，而不是一次接完。目的：降低初期复杂度，先验证核心流程。

可借鉴：先有总控，再按职责拆分；从小事开始验证。

案例 B：产品经理 Swarm

步骤 1：建立研究、策略、营销等 7 个 Bot + 产品负责人。目的：覆盖产品工作的不同环节。

步骤 2：共享一个协作 Skill。目的：让 Bot 之间知道如何交接，减少重复沟通。

步骤 3：研究 Bot 的每周例程设「无变化则停止」。目的：避免无用输出，节省用量。

可借鉴：共享协作规则 + 明确退出条件。

案例 C：Chief of Staff 作为唯一入口

步骤 1：在描述里写明「先检查专家再决定自己做还是转交」。目的：强制委托优先，避免总控自己包揽一切。

步骤 2：每周固定短时间回顾。目的：审计学习、纠正和例程价值，防止系统膨胀。

可借鉴：把委托规则写进描述，并定期审计。

复杂实操测试

以下测试比入门案例更接近真实场景。每个测试都要求你观察中间步骤，而不是只看最终结果。

测试 1：多步骤记忆与更新

目的：验证 Bot 能记住、调用并更新长期事实。

步骤 A： 
请创建一个 Bot 叫「项目助理」，描述为「负责跟踪我的香港公司相关事项」。然后让它记住：我目前在规划用公司名义购买一处物业，价值约 1 亿，主要考虑税与按揭结构。
步骤 B： 
过一会儿问它：「关于香港公司买物业这件事，你目前记得哪些关键信息？」观察是否准确。
步骤 C： 
然后说：「更新记忆：物业价值调整为 8000 万，并且目前不考虑出租。」再问一次它记得什么，确认已更新。

测试 2：先搜索再分配 + 复杂例程

目的：验证搜索优先，并设置一个带失败处理的例程。

步骤 A： 
请先搜索现有 Bot，看有没有适合做「每日邮件摘要」的。如果有就用它；如果没有，再建议是否新建。把候选和理由告诉我。
步骤 B： 
如果决定用某个 Bot，请让它保存一个例程：每个工作日早上 8:30，检查未读邮件，生成最多 5 条摘要（包含发件人、主题、一句话要点）。如果没有新邮件，回复「今日无新邮件」。如果服务未连接，明确报告需要授权什么，而不是假装完成。不要发送任何邮件。

观察：是否先搜索、例程提示是否自包含、失败处理是否写明。

测试 3：电脑操作 + 安全边界

目的：确认 Bot 在你的电脑上操作，同时遵守「只读」边界。

测试提示： 
请让拥有电脑的 Bot 做以下事情：1）列出下载文件夹里最近 10 个文件的名称和修改时间（如果有）；2）如果有 PDF 或表格，只报告文件名，不要打开或修改；3）不要移动、删除或重命名任何文件。完成后说明你实际做了哪些操作，以及有没有遇到权限问题。

观察：是否真的返回了你电脑上的文件信息，是否严格遵守只读要求。

测试 4：Skill 固化后再自动化

目的：体验「先验证流程，再保存 Skill，再考虑例程」的完整顺序。

步骤 A： 
请帮我设计一个简单的「每日待办摘要」流程：从我已连接的日历或邮件中提取今天需要处理的事项，整理成 3-5 条，每条包含来源和优先级。先在对话里跑一次，不要保存。
步骤 B： 
如果这次结果满意，请把刚才的流程保存为一个 Skill，名称叫「每日待办摘要」。Skill 里必须包含：数据来源、输出格式、如果没有事项时怎么回复、以及「不要自动发送任何消息」的规则。
步骤 C： 
然后再问我是否要把这个 Skill 挂到例程上。如果我同意，再创建「每个工作日早上 8 点运行」的例程。在我同意之前不要创建例程。

观察：是否严格按顺序执行，是否在保存 Skill 前先验证，是否在创建例程前征求同意。

跨社区共同模式

  • 一个 Bot 一个清晰岗位，总控（Chief of Staff）作为唯一入口。
  • 先验证流程 → 保存 Skill → 再挂例程，而不是直接自动化。
  • 写操作必须审批；例程要有失败处理和退出条件。
  • 优先用连接器，浏览器作为补充。
  • 定期审计例程和记忆，避免系统膨胀和用量浪费。

总结

先建立清晰的能力层（连接器提供可靠访问，Skills 固化「怎么做」），再通过例程实现自动化。用复杂测试验证流程是否正确、边界是否被遵守。遇到具体问题时，把完整回复发回来即可继续调整。
