Grok Bot 深度使用指南

Give a Bot the job, not the question · 先原理再实操

前言

借鉴 learngrok.dev 与 grokbot.dev 的组织方式：以「把工作交给 Bot」为核心，而不是反复提问。本指南把每个主题写成可独立阅读的详细说明，并配有可复制的测试场景。

核心顺序始终是：先搜索现有 Bot → 验证流程 → 保存为 Skill → 再挂例程。未验证的流程不要直接自动化。

核心原则

Give a Bot the job, not the question

learngrok.dev 反复强调这一点。普通对话是「问问题」，Bot 是「交办工作」。一个清晰的岗位描述比临时提示更重要。

好的岗位描述包含：职责范围、数据来源、输出格式、什么必须停下来等人确认。把长期规则写进 Bot 描述，而不是只放在聊天里。

一个 Bot 一个岗位

社区和 grokbot.dev 的大量模板都遵循这个原则。职责越单一，记忆越干净，例程越容易管理。重复创建或职责重叠是常见问题。

先搜索现有 Bot。如果已有接近的，优先调整描述或复用，而不是新建。

记忆与执行环境

每个 Bot 有独立长期记忆，并共享一台云电脑（浏览器、文件系统、终端）。登录会话可跨任务保留。敏感凭证不要放进记忆，走连接器。

复制 Bot 会保留描述、Skills 和例程，但不复制对话历史和学到的记忆，适合重置上下文时使用。

连接器、插件与 Skills

连接器优先

在「Connect apps」添加，一次登录后账号内所有 Bot 可用。优先使用连接器，比纯浏览器点击更稳定。用 @ 引用连接器，用 / 引用 Skill。

没有连接器的服务仍可通过共享电脑的浏览器操作，但需要先登录一次。

Skill 的完整结构

一个可用的 Skill 应写明：何时使用、需要哪些输入与权限、步骤、如何验证结果、输出格式、哪些动作必须审批。

正确顺序：先在对话里做对 → 明确要求保存为 Skill 并补充边界 → 在安全输入上测试 → 稳定后再考虑例程。

Teach a Task

观察你完成一次浏览器流程（约 10 分钟）后生成草稿。必须手动补充决策规则、失败处理和审批边界，并在测试输入上验证。不要在演示中暴露密码。

例程与自动化

例程 = 负责的 Bot + 触发条件 + 已验证的流程。提示必须自包含：数据来源、处理逻辑、输出格式、无数据时怎么办、哪些动作必须停下来确认。

限制参考：单 Bot 最多约 50 个例程；间隔至少 5 分钟；保留最近约 20 条记录；删除不可恢复。隐藏 Bot 不会停止例程。

先用 Test run 验证，再正式启用。高频例程会快速消耗用量。定期审计哪些还在产生价值。

正确交互流程

  1. 先搜索现有 Bot，避免重复创建。
  2. 异步发送并持续等待最终结果。
  3. 流程验证通过后保存为 Skill。
  4. 需要自动化时再创建例程，并写清失败处理与审批。
  5. 多个 Bot 可能承担同一职责时，先列出候选让你选择。

进阶模式

四要素

Context（你是谁与约束）、Connections（可靠工具访问）、Capabilities（已验证 Skills）、Cadence（例程节奏）。缺一不可。

Chief of Staff 作为唯一入口

日常只和总控对话。描述里写明「先检查专家再决定自己做还是转交」。每周短回顾：学到了什么、被纠正过两次的地方、哪些例程该关。

Outer / Inner Loop

一个 Bot 只做调研并产出自包含任务说明，另一个只执行。减少上下文污染。

社区案例

一人公司多 Agent

先建 Chief of Staff，再按角色逐步添加专家。每个重复任务单独绑定例程。工具逐步连接。

产品 Swarm

多个岗位 Bot + 共享协作 Skill。研究例程设「无变化则停止」。

小红书工作流（国内）

总助 + 情报 + 运营 + 美工。强调「源文从我来、数字从报告来、发布我点」三道硬门。只对总助说话。

复杂实操测试

测试 1：记忆与更新

请创建「项目助理」，记住：我在规划用香港公司名义购买物业，价值约 1 亿，主要考虑税与按揭。之后问它记得什么，再更新为 8000 万且不考虑出租，确认已更新。

测试 2：先搜索 + 带失败处理的例程

先搜索是否已有适合做每日邮件摘要的 Bot。如果有就用它；没有再建议。然后让它保存例程：每个工作日 8:30 生成最多 5 条未读邮件摘要。无新邮件时回复「今日无新邮件」。服务未连接时明确报告需要授权什么。不要发送任何邮件。

测试 3：先验证再固化

先在对话里跑一次「每日待办摘要」（从日历或邮件提取今天事项，3-5 条）。满意后再保存为 Skill，包含数据来源、输出格式、无事项时怎么回复、以及不要自动发送的规则。在我同意之前不要创建例程。

总结

把工作交给有清晰岗位的 Bot，而不是反复提问。先建立可靠的能力层（连接器 + Skill），再自动化。用复杂测试验证边界是否被遵守。
