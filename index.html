Grok Bot 中文指南

融会 learngrok.dev 与 grokbot.dev · 从入门到安全使用

前言

learngrok.dev 把内容组织成 Guides、Prompts、Workflows、Fixes，强调「把工作交给 Bot，而不是反复提问」。grokbot.dev 则提供大量可直接安装的 Bot 模板和 Collections，按岗位和场景分类，并有「Start Here」入门合集。

本站把两者的核心内容整理成中文，方便直接阅读和使用。重点包括：入门路径、核心原则、安全连接、任务简报写法、例程机制，以及社区模板中反复出现的模式。

从这里开始

grokbot.dev 的 Start Here 思路

该合集针对「第一小时最难」设计了 5 个 Bot：

  1. 引导式第一小时：让新手看到 Bot 实际能做什么。
  2. 五分钟入门 Bot：问几个问题后生成匹配的起步 Bot，并提示连接工具。
  3. Bot 构建器：回答少量问题后生成结构完整的 Bot。
  4. 审计与调优 Bot：从具体工作出发，检查并优化已有 Bot。
  5. 安装前审查 Bot：在把别人分享的 Bot 加入账号前先检查，避免直接信任。

实际可借鉴的顺序：先用一个简单引导理解能力 → 快速生成起步 Bot → 用审计 Bot 检查 → 安装任何外部模板前先审查。

learngrok.dev 的起步项目

他们建议从有明确产出的小项目开始：做一个会跑的 Bot、把一个重复任务变成命令、或完成一个可验证的工作流。每个都强调「最后有东西真正运行」。

核心原则

Give a Bot the job, not the question

这是 learngrok.dev 最核心的表述。普通对话是问答，Bot 是交办工作。清晰的岗位描述（职责、数据来源、输出格式、审批边界）比临时提示更重要。

把长期规则写进 Bot 描述，而不是只放在聊天里。

一个 Bot 一个岗位

grokbot.dev 上大量模板都遵循这个原则。职责越单一，记忆越干净，例程越容易管理。先搜索现有 Bot，优先复用。

先验证再固化再自动化

两个站点的实践都指向同一顺序：先在对话里把流程做对 → 保存为 Skill 并补充边界 → 在安全输入上测试 → 稳定后再挂例程。

Bot 基础与区别

Bot 与普通对话的区别

learngrok.dev 明确指出：Bot 是有电脑的代理。所有 Bot 共享一台云电脑（浏览器、文件系统、终端）。登录会话可跨任务保留。工作可以在你关闭设备后继续。

这解释了大部分能力和限制：它能操作已登录的网站和文件，但所有 Bot 共享同一套登录状态，因此连接工具时要考虑范围。

如何获得 Grok Bot

通过 Cursor 购买和下载，而不是直接从 x.ai。具体计划是否包含、平台是否有构建版本、以及账号设置是否阻止使用，都需要确认。官方文档是最终依据。

连接器、插件与 Skills

连接器优先

在「Connect apps」添加，一次登录后账号内所有 Bot 可用。优先使用连接器，比纯浏览器点击更稳定。用 @ 引用连接器，用 / 引用 Skill。

learngrok.dev 强调：所有 Bot 共享一台电脑和一套登录。这决定了你应该如何连接任何东西。

Skill 与 Teach a Task

Skill 应包含：何时使用、输入与权限、步骤、如何验证、输出格式、哪些动作必须审批。Teach a Task 可生成草稿，但必须手动补充规则、失败处理和审批边界，并在测试输入上验证。

安全运行与审批

什么会让 Bot 停下，什么不会

learngrok.dev 指出：没有固定的「必须审批」动作列表。有三套机制决定是否暂停。人们最容易误读的是「always allow」规则。发送、支付、删除、发布、改生产等动作，应在 Skill 和例程里明确要求停下来确认。

安全连接工具

因为所有 Bot 共享同一台电脑和登录状态，连接时要考虑最小权限。安装别人分享的 Bot 前，先审查其描述和权限要求，而不是直接信任。

常见故障方向

learngrok.dev 的 Fixes 类别包括：网站反复要求登录、Bot 卡住等待或未经询问就行动、电脑不可达、插件安装或认证失败、定时例程未运行等。遇到问题时先检查连接状态、审批设置和例程记录。

任务简报写法

learngrok.dev 提供了任务简报模板思路。一个好的简报应包含：

  • 范围：要完成什么
  • 输入：数据从哪里来
  • 边界：什么不能做，什么必须停下来确认
  • 完成定义：返回什么格式，如何验证

示例结构：目标 + 来源 + 限制 + 交付物 + 确认节点。这在国内中文教程中也有类似表述。

例程与自动化

例程 = 负责的 Bot + 触发条件 + 已验证的流程。提示必须自包含。限制参考：单 Bot 最多约 50 个；间隔至少 5 分钟；保留最近约 20 条记录；删除不可恢复。隐藏 Bot 不会停止例程。

先用 Test run 验证，再正式启用。高频会快速消耗用量。定期审计哪些还在产生价值。

模板与社区模式

grokbot.dev 的模板风格

大量模板用一句话描述岗位，例如「Opens the weekday with a brief and hands work to your bots」，并带上 tags（scheduled、agent team、productivity、personal）。可直接作为描述起点，再按自己的约束调整。

常见分类包括：Chief of Staff & orchestrators、个人效率、财务监控、内容创作、工程与研究等。

社区共同模式

一个 Bot 一个岗位、总控作为唯一入口、先验证再自动化、写操作必须审批、例程要有失败处理和退出条件、定期审计。国内小红书工作流也强调「源文从我来、数字从报告来、发布我点」三道硬门。

实操测试

测试 1：记忆与更新

请创建「项目助理」，记住：我在规划用香港公司名义购买物业，价值约 1 亿，主要考虑税与按揭。之后问它记得什么，再更新为 8000 万且不考虑出租，确认已更新。

测试 2：先搜索 + 带失败处理的例程

先搜索是否已有适合做每日邮件摘要的 Bot。如果有就用它；没有再建议。然后让它保存例程：每个工作日 8:30 生成最多 5 条未读邮件摘要。无新邮件时回复「今日无新邮件」。服务未连接时明确报告需要授权什么。不要发送任何邮件。

测试 3：先验证再固化

先在对话里跑一次「每日待办摘要」（从日历或邮件提取今天事项，3-5 条）。满意后再保存为 Skill，包含数据来源、输出格式、无事项时怎么回复、以及不要自动发送的规则。在我同意之前不要创建例程。

总结

把工作交给有清晰岗位的 Bot，而不是反复提问。先建立可靠的能力层（连接器 + Skill），注意共享电脑带来的权限范围，再通过例程自动化。用测试验证边界是否被遵守。遇到具体问题把完整回复发回来即可继续调整。
